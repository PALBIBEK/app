# D3 — Catalog & harness bind

**Status:** PASS (2026-08-30) — verify cycle 2 scored 32/32; next scope D4  
**Wave:** 1 (after D1 auth + D2 ready gates; before D4 sessions/SSE)  
**Depends on:** D1 (`AiClient` + service credentials), D2 (`run_allowed` / platform status)  
**Goal:** Product `harness.id` owns an immutable AI pin (`harness_version` + `composition_digest`). Create/edit can produce a **runnable** harness; Test/Run only uses that pin—never free-form strings or mock chat.

**Done means (north star):**

> System maps `harness.id` → `harness_version` + composition digest. UI create/edit yields a runnable pin. Session create (D4) sends that pin to supervisor; digests are content-addressed and immutable.

---

## 1. Why D3 exists

Two different things are both called “harness”:

| Plane | Concept | Identity | Runnable? |
|-------|---------|----------|-----------|
| **System / UI** | Product config (name, model, tools, prompt) | UUID `harness.id` | Not by itself |
| **AI** | Versioned agent behavior + composition pins | `harness_version` + digests | Yes — session create |

Until they are bound:

```text
UI “Create Harness” → system row (CRUD only)
UI “Test”           → mock chat (today)
AI “Run”            → needs harness_version + composition_digest
```

D3 closes the middle:

```text
UI create/edit
  → system harness row
  → bind / publish → (harness_version, composition_id, composition_digest, runtime)
  → runnable when: pin valid + catalog offered + D2 run_allowed
  → D4: BFF POST /v1/sessions with stored pin only
```

**UI surfaces that depend on D3**

| UI | Need |
|----|------|
| `/harness/new` | Persist + optional Draft vs Publish/bind |
| `/harness/[id]` tabs | Show bound tool_set / prompt_pack / memory / sandbox digests |
| **Test** / **Test Harness** | Enabled only when bound + offered + `run_allowed` |
| Dashboard cards | Publish/bind badge, not fake “Active” alone |

## 2. Architecture rules (freeze)

1. **Product harness ≠ AI harness version** — same English word, different IDs; always map explicitly.  
2. **Sessions store digests, never floating tags** (`latest` forbidden) — `contracts/composition.md`.  
3. **Browser never calls** `/v1/catalog` or `/v1/sessions` (D1).  
4. **BFF sends stored pins only** — client must not supply arbitrary digests on Run.  
5. **Republish = new digest** — never mutate an offered body in place.  
6. **Draft ≠ runnable** — Test requires offered bind + D2 ready.  
7. **Mode for Run** aligns with AI: `sticky` \| `stateless` (not system’s `chat` \| `completion` \| `agent` unless mapped).

## 6. Target design for D3

### 6.1 Pin model (system-owned)

```text
HarnessBind (columns on harness or 1:1 table)
  harness_id
  harness_version          # e.g. coding-v1
  runtime                  # echo | harness | githi
  composition_id           # e.g. coding-v1
  composition_digest       # sha256:…
  bind_status              # unbound | bound | stale | error
  bound_at / bound_by
  # optional denormalized for UI:
  prompt_pack_digest, tool_set_digest, …
```

### 6.2 MVP vs full publish

| Approach | When | Behavior |
|----------|------|----------|
| **Pin-only (MVP)** | Prove vertical slice fast | Bind every product harness (or selectable) to shipped `coding-v1` digest + matching `harness_version` / `runtime` |
| **Derived publish** | Product depth | On Publish: build PromptPack/ToolSet from UI → `POST /v1/catalog/{kind}/publish` → store new digests on bind |

MVP is enough to unlock D4. Full publish can follow in the same dimension without blocking sessions.

### 6.3 Runnable definition

```text
runnable =
  bind_status == bound
  AND composition status == offered (last validated)
  AND D2.run_allowed
```

### 6.4 Flows

**Bind (MVP)**

```text
User selects composition (or default coding-v1)
  → System AiClient GET catalog composition by digest
  → Validate offered
  → Persist pins on harness
  → Return harness + bind in API
```

**Publish (full)**

```text
User edits prompt/tools → Publish
  → System publishes prompt_pack + tool_set (+ composition)
  → Store new digests; deprecate previous composition if policy says so
  → bind_status = bound
```

**Run (D4 consumes)**

```text
POST system /sessions (future)
  → load owned harness + pins
  → if !runnable → 422/503
  → AiClient POST /v1/sessions {
       harness_version, runtime,
       composition_id, composition_digest
     }
```

### 6.5 UI bind status (required)

| Field | UI |
|-------|-----|
| Publish/bind status | Badge: Draft / Runnable (Offered) / Deprecated / Stale |
| Harness version | Monospace chip |
| Composition id @ digests | Truncated `sha256:` + copy |
| Child pins | Collapsible prompt/tool/memory/sandbox |
| Platform ready | D2 banner (independent) |

**Test gate**

| Bind | `run_allowed` | Test |
|------|---------------|------|
| unbound / draft | any | Disabled |
| bound + offered | false | Disabled (D2) |
| bound + offered | true | Enabled → real BFF (D4) |
| stale / deprecated | any | Disabled or force rebind |

## 8. Implementation order (recommended)

1. **Freeze vocabulary** — product harness vs `harness_version` vs composition; mode mapping table.  
2. **System migration** — pin columns + schemas + response `bind` object.  
3. **AiClient catalog methods** — list/get compositions (D1 client).  
4. **MVP bind endpoint** — pin to shipped `coding-v1` (or picker of offered compositions).  
5. **Supervisor harden** — version match + optional require-digest flag.  
6. **UI** — show bind; wire create/edit persist; gate Test with D2.  
7. **Ops** — persist catalog; document digest recompute CI (`harness/scripts/recompute-digests.py`).  
8. **(Optional same wave)** Derived publish from prompt/tools.  
9. **Hand off to D4** — session BFF uses pin helper only.

## 11. Definition of done

D3 is **done** when:

1. A product harness can be **bound** to an offered composition digest and that pin is visible in the API/UI.  
2. Unbound/draft harnesses cannot claim Test works.  
3. The D4 session path has a single helper that loads pins—no ad-hoc `harness_version` strings from the browser.  
4. AI catalog immutability rules are respected (digest pins, persist in prod).  
5. Mode/status vocabulary no longer silently disagrees across UI and system for the Run path.

Then proceed to **D4** (sessions + SSE), reusing D2 `run_allowed` and D3 pins.
