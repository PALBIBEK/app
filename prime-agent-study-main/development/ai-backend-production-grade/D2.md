# D2 — Health / ready gates

**Status:** PASS (2026-08-30) — verify cycle 1 scored 24/24; residual soft-skip memory documented in `contracts/readiness.md`  
**Wave:** 0 (after D1; before D3 catalog bind and D4 sessions/SSE)  
**Depends on:** D1 (`AiClient` + service credentials) — without D1, ready probes from the system backend are either impossible or insecure  
**Goal:** The product refuses **Run / Test chat / send message** when the AI plane is not ready. Ops probes stay honest. Secrets required for a “ready” production profile are not optional.

**Done means (north star):**

> System refuses Run if AI is not ready. Authenticated `platform/status` aggregates supervisor (+ gateway + memory). UI disables Test/send and shows a banner. K8s `/ready` on the system BFF stays system-DB-only; AI readiness is a separate product gate.

---



## 1. Why D2 exists

D1 makes AI calls *trusted*. D2 makes them *conditional*:

```text
Browser ──user JWT──► System BFF
                         │
                         ├─ GET /api/v1/platform/status  ← product gate (D2)
                         ├─ POST sessions…               ← same ready check (D4+)
                         │
                         └─ service credential ──► Supervisor /readyz
                                              ├──► Gateway  /v1/readyz (new)
                                              └──► Memory   /v1/readyz (new)

K8s system:  GET /health, GET /ready     → system process + system DB only
K8s AI:      /healthz + /readyz          → per-service probes
```

Without D2:

- Harness **Test** still “works” via **mock** chat even when AI is down.
- Supervisor can report ready while gateway has no API keys or memory is unreachable.
- Staging can start supervisors with `depends_on: service_started` before gateway accepts traffic.

**UI surfaces that depend on D2**


| UI                                   | Behavior when not ready                     |
| ------------------------------------ | ------------------------------------------- |
| Dashboard / harness card **Test**    | Disabled or blocked with reason             |
| Harness detail **Test Harness**      | Same                                        |
| `/harness/[id]/test` send            | Banner + send disabled; **no mock success** |
| Sessions **New** / message send (D4) | BFF returns `503 AI_PLATFORM_NOT_READY`     |
| Optional header chip                 | “AI platform unavailable”                   |

## 2. Architecture rules (freeze)

1. **Split probes vs product status**
  - System `GET /health` + `GET /ready` = BFF process + **system** Postgres only.
  - Do **not** put AI checks into system `/ready` (AI outage must not eject login/CRUD from the load balancer).
2. **Browser never probes AI** — no `NEXT_PUBLIC_SUPERVISOR_URL` health calls (align with D1).
3. **UI disable ≠ security** — mutating AI proxies must fail closed with the same ready helper.
4. **Liveness stays cheap** — `/healthz` never calls upstream vendors or durable stores.
5. **Readiness is honest** — “ready” means required deps for Run can succeed, not merely “process responds”.
6. **Public vs protected** — health/ready may stay public for probes; `/metrics` and product `/v1/`* follow D1 (auth in prod). Health under `/v1/healthz` needs an explicit probe exception.

## 3. What exists today



### 3.1 Supervisor — real shapes, shallow in places


| Endpoint       | Role      | Checks                                                                                               |
| -------------- | --------- | ---------------------------------------------------------------------------------------------------- |
| `GET /healthz` | Liveness  | Process only                                                                                         |
| `GET /readyz`  | Readiness | Configured → not draining → DB `SELECT 1` → sandbox callback (if any) → composition catalog problems |
| `GET /metrics` | Ops JSON  | In-process counters — **unauthenticated**, not Prometheus                                            |


**Readyz strengths**

- Drain → 503 `draining`; create session refuses while draining.
- DB ping wired in `build_supervisor`.
- Catalog pin problems can fail ready.
- Unit tests: ok, draining, db failure (`tests/unit/test_health.py`).
- K8s: readiness → `/readyz`, liveness → `/healthz`.
- Staging compose: supervisor HTTP healthcheck on `/readyz`.

**Readyz weaknesses**


| Issue                                        | Evidence                                |
| -------------------------------------------- | --------------------------------------- |
| Sandbox check is a no-op `return True`       | `app.py`                                |
| **No** gateway HTTP probe                    | Ready while LLM edge is down            |
| **No** memory HTTP probe                     | Ready while durable memory is down      |
| Catalog load can be disabled → check skipped | `YAL_LOAD_COMPOSITION_CATALOG=false`    |
| Auth/secrets not part of ready               | Overlaps D1 fail-closed                 |
| Messages not gated on drain                  | Only create is refused                  |
| K8s `preStop: sleep 5` before SIGTERM        | Still Ready ~5s while accepting creates |
| No `startupProbe`                            | Slow boot can flap liveness             |


Paths: `services/supervisor/src/supervisor/api/health.py`, `app.py`, `session/lifecycle.py`, `deploy/k8s/supervisor-deployment.yaml`.

- Correct for k8s BFF readiness; **insufficient** for product Run gates.

| Surface                        | Today                                                             |
| ------------------------------ | ----------------------------------------------------------------- |

### 3.6 Trust / ready map (current)

```text
System /ready     → system DB only          ✅ for k8s BFF
Supervisor /readyz → DB + drain + catalog   ⚠️ false-ready on gateway/memory/sandbox
Gateway /healthz  → process                 ❌ not a Run signal
Memory /healthz   → process                 ❌ not a Run signal
UI Test chat      → mock                    ❌ never refuses
System platform/status → missing            ❌
```

## 5. Target design for D2



### 5.1 Ready hierarchy

```text
System “run_allowed?”
  └─ GET supervisor /readyz   [required]
        ├─ configured, not draining
        ├─ database
        ├─ catalog (prod: ≥1 valid offered composition)
        ├─ sandbox (if provider ≠ none): real ping
        ├─ GET {GATEWAY}/v1/readyz     [required when URL set / always in prod]
        └─ GET {MEMORY}/v1/readyz      [required if policy=required or MEMORY_SERVICE_URL set for product]
```

Use `/healthz` only for liveness — **never** as the Run gate.

### 5.2 System platform status API

`GET /api/v1/platform/status` — requires `CurrentUser`

```json
{
  "ready": false,
  "run_allowed": false,
  "checked_at": "2026-08-29T15:30:00Z",
  "components": {
    "supervisor": { "ready": false, "status": "not_ready", "reason": "gateway" },
    "gateway":    { "ready": false, "status": "not_ready", "reason": "credentials" },
    "memory":     { "ready": true,  "status": "ok" }
  }
}
```


| Rule                  | Detail                                             |
| --------------------- | -------------------------------------------------- |
| HTTP for GET status   | Prefer **200** + `ready:false` (UI-friendly)       |
| HTTP for AI mutations | **503** + `AI_PLATFORM_NOT_READY` when not ready   |
| Reasons               | Safe enums only — no hosts, tokens, or SQL         |
| Timeouts              | 1–2s per component; parallel; short TTL cache      |
| Prod misconfig        | Missing AI URL/token → `ready:false` (fail closed) |




### 5.3 Gateway `/v1/readyz` (suggested)

200 only when:

1. Settings load; `routes()` non-empty and valid
2. Every route’s provider is registered
3. Non-`echo` providers have required API key env non-empty

Else 503 with reason `routes` | `provider` | `credentials`.

Echo-only profile: ready without vendor keys.

### 5.4 Memory `/v1/readyz` (suggested)

200 only when `MemoryService` started (`_ready`) and DB ping succeeds.  
Else 503 `not_configured` | `database`.  
`/v1/healthz` stays process-only; post-boot DB death → ready 503, health may stay 200.

### 5.5 Frontend behavior

1. Hook polls `/api/v1/platform/status` (focus refetch OK).
2. If `!run_allowed`: disable Test links and send; show banner with user-safe reason.
3. If send races: show toast from 503 — **never** append a simulated assistant message.
4. Remove/ignore `NEXT_PUBLIC_*` AI base URLs for health/chat.

## 7. Implementation order (recommended)

1. **Land D1 prerequisites** — `AiClient` + service Bearer to supervisor (else stop).
2. **Freeze contract** — ready reasons; required vs soft deps; system `/ready` vs `platform/status`.
3. **Gateway + memory** `/v1/readyz` — shallow but honest (credentials + DB).
4. **Harden supervisor** `/readyz` — probe gateway/memory; fix drain on messages; optional real sandbox check.
5. **Compose/k8s probes** — gateway (+ memory) healthy; startupProbe; preStop drain.
6. **System** `platform/status` — aggregate + cache + tests.
7. **Frontend gate** — banner + disable; kill mock success path when status wired.
8. **Shared fail-closed helper** for future session BFF (D4).
9. **Hand off to D3** — catalog bind only offered when Run can actually work.

## 10. Definition of done

D2 is **done** when:

1. A logged-in user sees **platform status** from the system API only.
2. **Test / Run / send** cannot pretend to succeed when AI is not ready.
3. Supervisor ready reflects **gateway** (and memory when required), not only local DB.
4. Gateway and memory expose **ready** distinct from liveness; staging waits on healthy deps.
5. System k8s `/ready` remains independent of AI outages.

Then proceed to **D3** (catalog & harness bind) and **D4** (sessions + SSE), reusing `run_allowed` so create-session never races a green button.
